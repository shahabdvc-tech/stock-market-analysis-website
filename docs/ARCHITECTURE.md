# معماری پیشنهادی

```text
کاربران وب --> WordPress (عضویت، پرداخت، رابط داشبورد/چت)
                         |
                         v
              Analysis Gateway (احراز هویت، سهمیه، کش)
                         |
            +------------+------------+
            |                         |
     Engine تحلیل عددی          AI orchestration
            |                         |
            v                         v
   Supabase read-only           OpenAI API
            ^
            |
     سامانه گردآوری موجود [بدون تغییر]

ChatGPT App/MCP (فاز بعد) --> OAuth --> همان Analysis Gateway
```

## اصول
1. جداسازی جمع‌آوری داده از محصول تجاری: پایگاه داده فعلی فقط منبع خواندن است؛ کرون‌ها، Edge Functionهای گردآوری، سهمیه‌ها و سیاست‌های نگهداری دست‌نخورده می‌مانند.
2. حساب‌ها و پرداخت‌های سایت در وردپرس یا دیتابیس تجاری مستقل؛ اتصال آن به Gateway از راه توکن کوتاه‌عمر با احراز هویت سروری.
3. دسترسی DB حداقل مجوز/فقط خواندن، بدون لو دادن service-role key یا BrsApi API key در مرورگر یا GitHub؛ RLS و کنترل سرور.
4. کنترل نرخ، quota روزانه/ماهانه، ثبت مصرف بدون ذخیره اطلاعات محرمانه، کش برحسب زمان و پارامترهای فیلتر.
5. موتور تحلیل داده خام حجیم را مستقیماً به LLM نمی‌فرستد؛ خروجی کوچک ساخت‌یافته با تاریخ و محدودیت داده ارسال می‌کند.
6. چت سایت با OpenAI API و محدودیت توکن و تعداد ابزار؛ قطع هزینه خودکار در آستانه بودجه.
7. MCP در فاز بعد، با OAuth و بررسی مجدد دسترسی در هر درخواست و بدون endpoint عمومی داده خام.
8. بررسی کارایی، load test، رصد خطا و backup قبل از عرضه.

## پیشنهاد استقرار اقتصادی
وردپرس روی هاست موجود در صورت سازگاری، محاسبات Backend سبک روی محیط جدا یا همان هاست در صورت توان فنی، و Supabase موجود. پردازش سنگین تاریخچه، Cron تحلیل‌های تجمعی و هزینه ناشی از ترافیک باید با تست واقعی اندازه‌گیری شوند.

## امنیت
عدم انتشار کلید، محدودیت خروجی، audit، session timeout، CSRF/CORS مناسب، تصدیق webhook پرداخت، نرخ‌گذاری per-user، جلوگیری از SQL دلخواه و عبور از سهمیه.
